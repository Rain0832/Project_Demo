## 一、这个 BUG 算不算“死锁”？符合四个必要条件吗？

### 结论先行

> **是死锁的一种形式（自死锁 / self-deadlock）**
> **完全符合死锁的四个必要条件**

哪怕 **只有一把锁、只有一个 goroutine**，也依然可以死锁。

---

### 1️⃣ 互斥条件（Mutual Exclusion） ✅

```go
var mu sync.Mutex
```

* `sync.Mutex` 天然是互斥的
* 同一时刻只能被一个 goroutine 持有

---

### 2️⃣ 请求并保持（Hold and Wait） ✅

你在 `AddUser` 里：

```go
s.mu.Lock()
...
s.LoadUser() // 里面又 Lock
```

* goroutine **已经持有 mu**
* 又去请求 **同一把 mu**
* 同时保持已有资源

---

### 3️⃣ 不可剥夺（No Preemption） ✅

* Go 的 Mutex **不会被 runtime 强行抢走**
* 只能由持有者 `Unlock()`

---

### 4️⃣ 循环等待（Circular Wait） ✅（这是你疑惑的点）

> “这里只有一个线程，怎么会循环等待？”

**关键点：循环不一定是多个线程形成的环**

这里的等待链是：

```
Goroutine A
 └─ 已持有 mu
     └─ 等待 mu（自己释放）
```

👉 **这是一个长度为 1 的等待环**

所以它仍然是循环等待。

---

### 一句话总结

> **不可重入锁 + 递归 / 间接调用 = 自死锁**

你这次踩的，是**教科书级但真实工程里极常见的死锁类型**。

## 一、先点破一个“隐患”（非常重要）

### 你现在的行为是：

* 每次 POST：

  * 读文件
  * 改 slice
  * 写整个文件
* 每次 GET：

  * 再读文件

### 问题是什么？

1️⃣ **性能极差（磁盘 IO 是内存的几千倍）**
2️⃣ **并发一高，文件是瓶颈**
3️⃣ **真实后端不会这么做**

---

## 二、真实后端是怎么做的？

### 核心思想一句话：

> **启动时加载到内存，运行时只操作内存，必要时落盘**

---

### 标准模式（你以后会反复见到）

```
程序启动
 └─ Load from storage (file / db)
     └─ 存到内存结构
         └─ 所有请求只操作内存
             └─ 修改后异步 / 同步写回
```

---

## 三、Level 12 的核心重构目标（不写代码也能懂）

### 你现在的 storage 是「文件即真相」

我们要改成：

### 🧠 内存即真相（source of truth）

```go
type FileUserStorage struct {
	mu    sync.Mutex
	users []User
	file  string
}
```

* `users`：**程序运行期间的唯一真相**
* 文件：只是 **启动加载 & 持久化备份**

---

## 四、你这一关要理解的 3 个关键设计点

### 1️⃣ 程序是“常驻进程”，不是脚本

* Web Server **不是跑完就退出**
* 内存状态是长期存在的

---

### 2️⃣ Handler 不该关心“文件”

Handler 只关心：

```go
storage.AddUser(...)
storage.ListUsers()
```

文件、锁、IO —— **都在 storage 内部**

---

### 3️⃣ storage 是一个“状态对象”

不是一堆函数，而是：

* 有生命周期
* 有内部状态
* 有明确职责
